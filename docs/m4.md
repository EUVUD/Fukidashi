# M4 Record

> 2026-10-29. Goal (OUTLINE §7, due 11/15): run all 3 configs on the dev split and get the first dev numbers (chrF / BLEU, COMET, term accuracy, cost, latency). First, set up COMET, check its checkpoint's license and memory, and estimate the cost against the budget cap.

## How to run

See "Run it" in the README. One dev pass is six eval runs (3 configs × 2 books) without `--pages`, then the two scorers on each run's directory, then one report over all six:

```bash
uv run python eval/run.py --config full --book boureisougi   # one of the six; whole book, in page order
uv run python eval/terms.py runs/eval/<id>                   # term accuracy: terms.json
uv run eval/comet.py runs/eval/<id>                          # COMET: comet-wmt22-comet-da.json
uv run python eval/report.py runs/eval/<id> [runs/eval/<id> ...]   # the pooled report: runs/report/<time>-report/
```

Nothing after `eval/run.py` calls a model provider. The report reads files only and refuses inputs that do not belong together.

## What was built

M4 was built as six tasks, each one PR with written acceptance criteria, an execution report and an independent review ([docs/workflow.md](workflow.md)). The decisions were recorded in #38, and a docs PR (#43) followed the scorers. Four of the tasks ran side by side, each executor in its own git worktree.

| Task | What it added | PR |
|---|---|---|
| Whole-book evals | The eval harness writes its outputs after every page, so an interrupted eval keeps the pages it finished; without `--pages` it evaluates every page of the book | #37 |
| CI | GitHub Actions on pull requests and pushes to `main`: the tests, the lint and the frontend build, with read-only permissions and no secrets | #39 |
| KB reach | A `full` Run records the items its KB snippets showed; the harness counts, per page and in total, the snippets shown, the lookups that found something or not, and the distinct items that reached a page | #40 |
| COMET scorer | `eval/comet.py`: `Unbabel/wmt22-comet-da` over a finished eval run, in an environment of its own, on the Mac's CPU | #41 |
| Term accuracy | `eval/terms.py`: the gold glossary's entries against a finished eval run, by the rules fixed before the dev runs (OUTLINE §4.7); a required `borderline` field in the glossary | #42 |
| Dev runs and the pooled report | Scorer fixes (split `segments.jsonl` on newlines only, record the COMET checkpoint's revision, refuse a repeated segment); `eval/report.py`, which pools finished eval runs into one report; then the six dev runs, scored and reported | #44 |

## Design decisions

The reasons are in [OUTLINE.md §8](../OUTLINE.md#8-decisions). The short form:

- **COMET only.** `wmt22-comet-da` runs on the Mac's CPU. XCOMET-XL's fp32 weights (about 14 GB) do not fit the Windows machine's 12 GB GPU, and COMET offers no lower precision, so the report gives COMET only.
- **Term accuracy before the dev runs.** It is the KB ablation's primary metric, so its rules were fixed before any whole-book output was read: names and coined terms only for the primary score, an occurrence only where the reference uses the term, occurrences pooled.
- **Scorers outside the translation path.** COMET and term accuracy read a finished eval run's files and write their own next to them, so a change of rules or checkpoint can score old runs again for free.
- **A report that refuses rather than guesses.** It compares configs on the pages every config scored, recomputes chrF and BLEU over the pooled segments instead of averaging books, joins COMET by segment key, and keeps unknown values unknown. Files that do not belong together (another eval run's scores, a changed `segments.jsonl`, another glossary) stop it with nothing written; provenance that does not change the numbers (a dirty tree, different commits) is a warning.
- **A budget and a stop rule for the dev runs.** At most $3, one eval at a time, and a stop when too many pages fail or 429s repeat.

The dev split has 79 pages with text (45 in `tojime_no_siora`, 34 in `boureisougi`) and 608 segments; the 3 pages without text were skipped. **No page failed and no call was rate-limited (HTTP 429)** in 684 calls. **The review loop.** In both `full_no_kb` and `full` the Reviewer approved 77 of 79 pages; one review was unusable and one page ended at the Send-back limit. There were 8 Send-backs in `full_no_kb` and 13 in `full`. No page fell back to `baseline`.

**The Curator and the KB.** The Curator was called on 12 of `full`'s 79 pages; the rest had no term proposal. Of 26 proposals, 11 terms were accepted, 3 rejected and 1 confirmed an existing entry; all 11 names went to the Human Review Queue. Each eval run's KB ended small: 8 approved entries and 3 pending profiles for `tojime_no_siora`, 3 approved entries and 8 pending profiles for `boureisougi`.

**KB reach.** The snippets part was not empty on 49 of 79 pages (22 of 45 and 27 of 34). Of 110 lookups, 44 found something. Of the 66 that found nothing, 38 asked for an item that entered the KB only on that page or later (a page's own proposals are invisible to it), 27 for an item that never entered it, and 1 for a term under the character lookup. At most two were near misses that normalisation could have caught (an honorific suffix, a kana name looked up in kanji). 15 distinct items reached a later page.

## What the numbers say

One run per config, no confidence intervals (the protocol's paired bootstrap is M8). With that caveat:

- **`full` vs `baseline` (primary metric COMET):** no gain on reference-based metrics. COMET is 0.0022 lower, chrF 0.16 higher, BLEU 0.73 lower. Page by page, `full` scored higher COMET on 40 pages and lower on 38. A paired bootstrap over pages, computed by hand for this record and not part of the protocol, puts the COMET difference between −0.008 and +0.004 (95%). `full` costs about 9.5 times as much per page and takes about 7 times as long (p50).
- **`full` vs `full_no_kb` (primary metric term accuracy):** the same pooled score, 61 of 117, and opposite signs per book (+3 occurrences in `tojime_no_siora`, −3 in `boureisougi`). COMET is 0.003 higher, within the same kind of spread.
- **Most of the difference between any two configs is sampling.** Only 165 to 178 of the 608 segments are identical between any two configs, about as many between `full` and `full_no_kb` as between `full` and `baseline`. The model runs with thinking on and is not deterministic; how far two runs of the same config differ on whole books has not been measured.

**Why term accuracy barely moves.** Most misses are valid renderings that differ from the reference translator's choice, which no config can know:

- In `tojime_no_siora`, 31 of the 63 primary occurrences belong to three entries that no config hit even once: a character name the system renders 蕾妮 where the reference has 蕾娜, a family name rendered 托尔蒂亚 against 托蒂亚, and an epithet rendered 闭眼 against 封着眼. The KB stored the system's own renderings (闭眼 approved, 蕾妮 pending) and kept them consistent from page to page. Term accuracy cannot see that consistency; term consistency (M5) can.
- In `boureisougi`, the KB held two pending profiles for one character with two renderings (one of them 铃, which the reference never uses; the other 樱野雀). On that entry `full` hit 1 of 10 occurrences, against 4 for `full_no_kb` and 2 for `baseline`. A name waiting for a person spread to later pages, the cost OUTLINE §8 accepted when it made pending entries readable. The same KB also split characters across profiles: a given name and a full name became two profiles for three characters, and one character's title (葬儀屋) became two more profiles while also being that character's alias (OUTLINE §3.3's open question on aliases).

What these findings mean for M5 (the eval protocol, tuning, and whether the KB ablation's primary metric stays) is decided there, before the freeze.

## Spend and time

M4 made 684 real calls, all of them the six dev runs (lines 73–756 of `runs/usage.jsonl`), for **$1.4208**, with no unknown usage and no failed call: `baseline` $0.087, `full_no_kb` $0.506, `full` $0.828. The estimate was about $1.3 (§7) and the cap $3. The scorers, the report and the rehearsal of the report on M3's runs made no call. The whole project's ledger stands at about **$1.51** of the $100 cap.

**Time.** M4 was planned at 3 hours for 11/9–11/15 and finished on 10/29. From M3's close (2026-10-28 13:40, local time) to the dev report (2026-10-29 02:09) is about 12.5 hours over six tasks and two docs PRs, of which the six dev runs themselves took about 1 hour 35 minutes. Executors ran side by side, so this is elapsed time, not effort. The hours in OUTLINE §7 are to be re-estimated at the 12/13 checkpoint (`IDEAS.md`).

## Not done / not verified

- **Statistics.** No confidence intervals (M8). Each config ran once, so the run-to-run spread on whole books is unknown.
- **The rest of the evaluation framework.** GEMBA-MQM and its judge model, the human agreement check and term consistency are M5. xCOMET is not reported (`IDEAS.md` keeps a CPU run on the Windows machine for M8).
- **The KB's open questions** (OUTLINE §3.3) now have dev evidence: names proposed under another name's alias become extra profiles, and pending names with conflicting renderings spread. Normalised matching is not needed on this evidence.
- **The report.** It records each input directory as typed on the command line, and it does not tie `terms.json` to the exact `segments.jsonl` it scored (only by eval id and glossary hash). Neither affected these runs (`IDEAS.md`).
- **The stop rule** was enforced by a launcher in `runs/`, whose stop path never fired on a real eval; a SIGINT sent to a process started with a shell `&` is ignored (`IDEAS.md`).
- **The editor and the API** still run `baseline` only (M7).
