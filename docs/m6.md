## How to run

The paired bootstrap reads files only and calls no model:

```bash
uv run python eval/bootstrap.py runs/eval/<id> ... --mqm-judge <model>   # runs/bootstrap/<time>-bootstrap/bootstrap.json
```

It takes the same eval runs as the pooled report: all three configs, one finished eval run per config and book. Every run must have its term accuracy, COMET, consistency and MQM files.

The test runs used the README's commands. They ran in a git worktree checked out at the tag, with `data`, `runs` and `.env` linked from the main checkout. They went one config and one book at a time, each book in the order `baseline`, `full_no_kb`, `full`:

```bash
uv run python eval/run.py --config baseline --book balloon_dream   # every page of the book
uv run python eval/terms.py runs/eval/<id>
uv run eval/comet.py runs/eval/<id>
uv run python eval/consistency.py runs/eval/<id>                  # judge calls
uv run python eval/mqm.py runs/eval/<id>                          # judge calls
uv run python eval/report.py <the nine eval runs> --mqm-judge gpt-4o-mini-2024-07-18 --mqm-agreement <agreement file>
```

These commands show what ran. Do not run them on the test books again: the protocol runs each config once and never reruns a failed page. A launcher wrapped each command and enforced the stop rules. It is a script under `runs/`, so it is not in the repository. It refused to start unless the worktree was at the tag and clean. It printed a line for every failed page and stopped a run on too many failed pages, a second HTTP 429 or a spending cap.

## Design decisions

The reasons are in [OUTLINE.md §8](../OUTLINE.md#8-decisions). The short form:

- **The test runs now, from the tag.** Responses name only `deepseek-flash`, so if the provider changed the model behind that name, nothing we record would show it. Running soon after the freeze keeps the tested model as close to the tuned one as we can make it (§9).
- **No request timeout.** A request that times out is not resent, so a timeout saves waiting time, not a page. The launcher warned after 20 minutes without progress, and a person could stop a run after 45 minutes.
- **The bootstrap's code before the first test page.** The protocol fixes the resamples, the seed and the pairing, but not every detail: each comparison's pages, or how a page drawn twice counts in term consistency. Because those details were written and merged before any test number existed, they cannot follow a result. MQM gets an interval too, for reference only. The consistency interval's label is decided per run, where a run is one config on one book.
- **The judge in M6.** OpenAI shuts GPT-4o mini down on 2027-01-14. Scoring right after the translations removes that risk.
- **A rehearsal first, on dev pages.** The launcher's stop path fired on a real eval: a $0.0005 cap led to a SIGINT and exit code 130. Then a three-page `full` run went through all four scorers.

### The six failed pages

All six are in `balloon_dream`, and the system caused none of them.

**`full_no_kb`, pages 7 and 10: the Mac slept.** The laptop's lid was closed in the run's first minute, and macOS sleeps a closed laptop even under `caffeinate -i`.
- **Page 7.** Its request died when the machine woke (`Connection error`).
- **Page 10.** Its request timed out after 618 seconds of awake time; the SDK's 600 seconds count awake time only.
- **Silence.** The longest stretch without progress was 40 minutes, which is under the 45-minute rule.
- **Distortions.** About 45 of the run's 70 minutes were sleep. One scored page, page 2, has its latency recorded short: 18.8 seconds for about 47, because `time.monotonic()` does not count sleep. By design, the pages after a failed page read less context from previous pages.

**`full`, pages 33, 36, 37 and 38: HTTP 402, "Insufficient Balance".** The DeepSeek account ran out of credit during page 33, and the next three pages failed on their first call, in about a second each. A 402 is rejected before the model runs, so these calls cost nothing. Their ledger lines have no cost and count as unknown.

A failed page is listed and never rerun (`eval/PROTOCOL.md`). These six pages are left out of the report's common pages, for every config.

### The waiver

The `full` run on `balloon_dream` reached its last page with 4 failed pages. That is one more than the stop rule allowed for that book: 3, the protocol's "more than about 10%" of 36. The rule fired after the run had ended, so nothing was cut short.

The executor stopped and asked the author how to count the run, with three options:
- **Report it as stopped.** By the task's wording, that would have dropped `balloon_dream` from the pooled report.
- **Waive the stop,** because the account caused the failures, not the system.
- **Rerun it.** That would break "each config once" and "no test page twice".

**The author waived the stop** ("Waive, go on", 2026-10-31 02:39 UTC). At that point the waived run had not been scored, and nobody had read a quality number of any test run. So the run counts as `balloon_dream`'s one `full` run, its four failed pages count like any other failed page, and the pooled report covers all three books. The author approved this record on 2026-10-31 (OUTLINE §8).

### Two steps the task did not name

After the waiver, the executor did two things the task had not listed:
- **One check call.** A single `baseline` call on a dev page (`tojime_no_siora` page 2, $0.0007) confirmed that the provider answered again before any more test pages went out.
- **`caffeinate -i -s` on AC power** for the second half of the runs, so the Mac could not sleep. The six later runs had no failed page and no gap.

Neither step touches a test Run. The executor disclosed both at once, and the author accepted both after the fact on 2026-10-31 (OUTLINE §8).

### What the numbers say

There is one run per config and no confidence interval yet; the next task computes the protocol's paired bootstrap, once. Unlike M5's dev numbers, these are held out: no prompt was tuned on these books, and each was translated once, from the tag. With those cautions:

- **`full` vs `baseline` (primary metric: COMET):** no gain.
  - On the reference-based metrics, `full` is lower: COMET by 0.0026, chrF by 1.34, BLEU by 2.28.
  - It costs about 8 times as much per page at the ledger's prices and takes about 5.4 times as long (p50). The ledger's figure is the upper end: with cached input priced as a range (#63), `full` costs 5.0 to 7.9 times `baseline` (OUTLINE §8, "Cost per page with cached input").
  - Its primary term accuracy is 2.6 pp higher (5 more of 189 occurrences), and its term consistency 4.6 pp higher.
- **`full` vs `full_no_kb` (primary metric: term accuracy):** no difference, 160 of 189 for both.
  - On the tuned dev runs, `full` was 5.1 pp ahead (73 against 67 of 117). That gap did not appear on the test books.
  - Term consistency, the secondary metric, is 2.6 pp higher with the KB (93.8% against 91.1%). On the tuned dev runs it was 11.0 pp higher.
- **The books differ.** `full`'s primary term accuracy is 13.6 pp above `baseline`'s on `tencho_isoro`, but 4.6 pp below it on `rasetugari`, the longest book. On `rasetugari`, `full` also has the highest consistency of the three configs, while more of its renderings differ from the reference's. Which entries those are is a question for M8's analysis. On the dev books, most misses were valid renderings that differ from the reference's: the KB keeps a rendering consistent, but it does not correct it (OUTLINE §9).
- **Most of the agent configs' difference comes from the first pass.** At least 121 of 124 pages in `full_no_kb`, and 118 in `full`, were approved at their first review. So nearly every stored Translation of the agent configs is the Translator Agent's first pass. Their difference from `baseline` comes from that pass (its prompt and the previous pages' context), not from the review.

## Lessons for the next paid run

`IDEAS.md` holds these:

- **Check the provider's balance against the estimate first.** A dry account fails every later call with a 402, and the eval harness has no consecutive-failure abort.
- **Keep the machine awake with the lid closed,** with `caffeinate -i -s` on AC power, and check `pmset -g log` afterwards. A sleep fails the requests in flight and distorts latencies.
- **A task must say how a call it does not list can be added** (a check call like the one above), and what a run that ends over the stop rule's limit counts as.
