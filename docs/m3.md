# M3 Record

> 2026-10-28. Goal (OUTLINE §7, due 11/8): a Knowledge Base with a Curator and a Proposal Queue, unit tests for KB write permissions, the Reviewer Agent in the full system (at most 2 rounds), a gold glossary for the dev split, and `baseline`, `full` and `full_no_kb` each run on one page. Every config ended up running on the same 3 pages.

## How to run

See "Run it" in the README: `eval/run.py --config full_no_kb` or `--config full`. `scripts/m3_review_smoke.py --dry-run` shows the flagging Translator's and the Reviewer's first requests without sending them. Add `--kb` to get the same requests with an empty KB. `eval/glossary.py check` validates the gold glossaries against the dataset.

## Design decisions

The reasons are in [OUTLINE.md §8](../OUTLINE.md#8-decisions) and §3.3. The short form:

- **Dev and test are split by book.** The dev books are `tojime_no_siora` and `boureisougi`; the other three are test books. `tojime_no_siora` cannot be a test book, because M0 to M2 read its output.
- **The gold glossary is drafted by a different model from the one it scores, then reviewed by the author.** It is evaluation data only. It never seeds the KB and never reaches a prompt.
- **A fresh KB for each eval run.** It fills page by page, in page order. Entries waiting for a person are readable, marked as pending. Otherwise no name would ever reach a later page, because every name waits for a person.
- **The Curator is code rules plus one model call.** Duplicates, confirmations, conflicts and names are decided by code, whatever the model answers. The model only judges whether a new term is worth keeping. It never sees a name proposal, the other agents' conversations or a reference translation.
- **Least privilege comes from what an agent has, not from its prompt.** The agents get an immutable snapshot and a proposal collector, never a database connection. A test checks that loading them does not load the database module.
- **One write per page, at finalize.** A page's own proposals are invisible to it until then. The KB changes only after the page's translation is final, so a page that fails writes nothing.
- **The Reviewer writes in Simplified Chinese.** The Translator reads its Issues when a page is sent back, and the editor will show them to a Chinese-reading user.
- **Agent requests are pinned.** `test_kb_seams.py` holds a digest of every request the agents send in 16 scenarios. A prompt change in M4 or M5 has to update them on purpose, in the same PR.

## Not done / not verified

- **Quality.** Each config ran on 3 pages, so there is no claim about quality. Whole dev books come in M4.
- **How often the KB reaches a page.** In the `full` run the KB's snippets matched nothing on any of the 3 pages, because retrieval matches exact strings. The one use of the KB across pages came through a lookup. The dataset spells one family name two ways on consecutive pages, and the KB ended with two approved entries with two different renderings. If this holds on whole books, the KB ablation will measure little. M4 measures it first (OUTLINE §9, `IDEAS.md`).
- **Failure paths.** A Curator with no usable answer, a failing KB write and the Reviewer's repair ran only against scripted providers and injected failures, not against DeepSeek.
- **Open KB questions** (OUTLINE §3.3): a term left undecided cannot be decided later; a failure after the KB write leaves the KB written under a failed Run; a character proposed under another character's alias becomes a second profile; a name proposed as a term is caught only by the Curator's judgment.
- **Traceability of the `full` run.** It ran on the task's uncommitted tree (its manifest says `git_dirty: true`), before review-driven edits that changed only a summary line, a docstring and tests.
- **Tracing.** The new root-span attributes were tested with an in-memory exporter, not checked in Phoenix. The Orchestrator's stages have no spans of their own (`IDEAS.md`).
- **The editor and the API** still run `baseline` only. Issues, flags and the Human Review Queue have no UI yet (M7).
- **Carried over** (`IDEAS.md`): a Run stays `running` if its process is killed; there is no server-side guard against a double click; eval outputs are written only after the last page; a `full` eval stopped by a missing `.env` leaves an empty KB behind.
