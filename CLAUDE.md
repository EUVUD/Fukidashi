## Project

- `OUTLINE.md`: design, milestones (§7), decisions (§8), pivot rules (§9). Its §0 Terminology table is canonical.
- `SCOPE.md`: what is in and out of scope, and the cut order. `IDEAS.md`: where ideas outside a checkpoint go.

## Architecture

One request shows the layering. In the browser, `PageView` POSTs `/api/pages/:book/:index/translate` (the Vite dev server proxies `/api`), then follows the Run's events at `/api/runs/:id/events`:

Invariants that span several files:

- Every model call goes through `LLMClient`, which enforces the per-page `PageBudget` and records each call in a `Meter` (ledger `runs/usage.jsonl`). Usage the provider does not return is unknown, never 0: it shows up as `unknown_usage_calls` and NULL token counts on the Run. A request that raised (timeout, connection error, any HTTP error), or whose response `LLMClient` cannot read (not a chat completion, no readable first choice), is still a call: it is recorded once with `error` set, then raised as `ProviderError`. Its usage is unknown unless the response carried some, so a ledger line can have both `error` and usage; totals key on usage, never on `error`. The SDK's own retries are off (`max_retries=0`), so every request sent is one call the `Meter` sees. `cost_usd` is NULL when any call had no usage or no price (`Meter.summary`); it is never a partial sum, and a Run with no calls costs 0.0. The eval harness keeps the same rule for totals (`cost_summary`) and reports scored and failed Runs' cost separately. **The judge** (GEMBA-MQM, term consistency) is a second `LLMClient` read from `JUDGE_*`, never the translation model, with a `Meter` and a ledger of its own (`runs/judge_usage.jsonl`, `config.JUDGE_LEDGER_PATH`): its calls are the evaluation's cost, never a Run's, and the $100 cap is the sum of both ledgers. The `Meter` writes no timestamps, so measure a task's spend by a ledger's line range. A provider hang is one call too. The eval's clients set no request timeout of their own (the SDK's 600 s applies); the API's set 180 s (`IDEAS.md`).
- Only `llm/` imports `openai`, only `agents/` imports `langchain` / `langgraph`, and only `tracing/` imports `opentelemetry` / `openinference` (nothing imports `phoenix`). Code outside `llm/` sees a provider failure only as `ProviderError` (`description`, `status_code`, and `record`: the call as the `Meter` has it), whose text never contains the API key.
- The agent loop (`agents/loop.py`): `LLMClientChatModel` calls `LLMClient.chat` once per model call, so agent calls are metered like any other, and nothing in the loop retries. DeepSeek's `reasoning_content` goes back unchanged on every assistant message, `""` included. `run_agent` returns an `AgentResult` of plain values (text, stop reason, error, steps, messages as OpenAI-format dicts) with one step per model call, a failed call included. Stop reasons: `final`, `step_limit` (`max_steps`, default 6), `incomplete` (a finish reason other than `stop` or `tool_calls`), `budget`, `provider_error`. A model's mistakes (unknown tool, arguments that fail the tool's pydantic `args`, a handler that raises) go back to it as the tool's result; a repeated call with the same validated arguments is not run again. Tool handlers run in LangGraph worker threads, the calls of one reply in parallel, so they must be thread-safe. `langsmith` comes with `langchain-core`, so `run_agent` refuses to start (`TracingEnabled`) while `LANGSMITH_TRACING`, `LANGSMITH_TRACING_V2`, `LANGCHAIN_TRACING_V2` or `LANGCHAIN_TRACING` is on: prompts would leave the machine.
- The Translator Agent (`agents/translator.py`): the user message is `baseline`'s (page image and regions), only the system prompt differs, and the answer must pass `parse_translations`. A bad answer gets one repair call (the history plus the parse error, JSON output, no tools); `step_limit`, `incomplete` or a failed repair fall back to `run_baseline` with its own budget (`fallback_budget`; the agent has `agent_budget`), and the Run stays `translator` and records why. `provider_error` and `budget` never fall back (OUTLINE §3.6). `get_previous_context` returns up to 2 earlier pages' Japanese and their latest succeeded `translator` translations, read by `runs.previous_pages` before the run starts, so the handler touches no database; reference translations never enter it. The eval harness reports `fell_back` per page and `fallback_pages` in `scores.json`. With `flagging=True` (the Orchestrator's runs) the agent also has `flag_uncertain` (a region id and a reason, collected under a lock; a boolean id is refused) and uses `FLAG_SYSTEM_PROMPT`; `TranslatorResult.flags` keeps the flags only when the answer is the agent's or its repair's. With `flagging` off, the default and the `translator` config, the requests are exactly M2's. With a `Revision` (the current translation and the Reviewer's Issues, added to the user message after `baseline`'s content), the run is a revision: same tools and repair, no fallback, and an answer it cannot use makes it `unusable`.
- With a `KBSnapshot` (`kb=`, which needs `flagging` and the page's own `ProposalCollector`):
  - **Tools.** The Translator also has `lookup_term`, `lookup_character` and `propose_entry`, and uses `KB_SYSTEM_PROMPT`.
  - **Snippets.** Its user message starts with one text part: the snapshot's snippets for the page (at most `KB_SNIPPET_CHARS`), or a line saying the KB has nothing for the page yet. The system prompt and the tools stay a stable prefix (OUTLINE §3.4).
  - **Proposals.** `propose_entry` validates through the collector, and so through `make_proposal`; a refused proposal goes back to the model with that message. `TranslatorResult.proposals` rebuilds the run's proposals from the arguments its steps recorded (`step_proposals`), in call order, and keeps, for each id, the payload of the first call in that order. The collector only answers the tool; what arrives first in it does not decide what is stored.
  - **Shared code.** The lookups, the snippets part and `KB_SNIPPET_CHARS` live in `agents/kb_tools.py`; the Reviewer imports them from there, never from `translator.py`.
  - **No snapshot** means none of this: every request is exactly what it was before.
- The Reviewer Agent (`agents/reviewer.py`, OUTLINE §3.2): `run_reviewer` takes plain values (the page, the translations by region id, the flags) and builds a fresh conversation: its own system prompt and one user message with the page image and each region's id, box, Japanese text and translation, plus the flags. It never sees the Translator's messages, reasoning or tool results, nor a reference translation. It runs through `run_agent`: with no tools by default, and with a `KBSnapshot` (`kb=`) with `lookup_term` and `lookup_character` only, its own `KB_SYSTEM_PROMPT`, and the same snippets part first. It answers `{"verdict": "approve" | "revise", "issues": [{"id", "comment", "suggestion"}]}`: at most one issue per region of the page, and `revise` needs one. Comments and suggestions are in Simplified Chinese (OUTLINE §8). A bad verdict gets one repair call. `ReviewResult.status` is `ok`, `unusable` (no verdict after the repair, or `step_limit` / `incomplete`: the translation stands) or `failed` (`provider_error` or `budget`: nothing more is sent). It has its own budget (`review_budget`, default 30,000 tokens) and raises `ValueError`, before any request, when the translations are not exactly the page's regions.
- The Orchestrator (`orchestrator/flow.py`, configs `full_no_kb` and `full`) is plain code: it takes plain values, returns a plain `OrchestratorResult`, and imports neither LangChain nor the database. Its flow:
  - The first pass is the flagging Translator, which may fall back to `baseline`.
  - The Reviewer reviews the current translation with the flags of the run that produced it.
  - A `revise` verdict sends the page back for a revision, at most `MAX_SEND_BACKS` (2) times. After the second revision there is no third review.
  - Every Translator run has `agent_budget` and every review has `review_budget`.
  - The loop's `final_stop` is `approved`, `review_unusable` (the current translation stands), `revision_unusable` (the previous translation stands) or `send_back_limit`.
  - `final_reviewed` says whether a review gave a verdict on the stored translation. That includes a `revise` verdict whose revision was unusable, so it does not mean "approved".
  - A `provider_error` or spent budget in any stage fails the whole Run, and no earlier stage's translation is stored.
  - Each earlier page's context comes from Runs of the same config.
  - `run_orchestrator(kb=None)` is `full_no_kb`. With a `KBSnapshot`:
    - one snapshot and one `ProposalCollector` serve the whole page, so a proposal is not visible to its own page's lookups;
    - `OrchestratorResult.proposals` (`merge_proposals`) lists the page's proposals by Translator run, then step, then position in the reply, keeps the first call's payload for each id, and is empty when the Run failed;
    - the attempts record says `"config": "full"`.
- The `full` config (`runs.py`, OUTLINE §3.3, §3.6) is the Orchestrator with the KB `kb_id`, then finalize:
  - **The KB.** `translate_page(config="full", kb_id=...)` needs a KB of the page's book. A missing, unknown or other book's KB, or a `kb_id` with another config, is a `ValueError` before any client or Run. The snapshot is loaded once, before the page, so every stage reads the KB as the page started.
  - **Finalize** runs only when the Orchestrator's page succeeded, in this order: the Curator Agent's call on the Run's client (its calls and cost are the Run's), then `curator.apply` in its own transaction (not called when the page has no proposals), then `store.finish_run`.
  - **The Curator Agent** (`agents/curator.py`): one call, no tools, no image. Its user message is the snippets part, each region's Japanese text and stored translation, and the page's `term` proposals; a `character` proposal, the other agents' conversations and the reference translations never reach it. It answers `{"decisions": [{"id", "accept", "reason"}]}`, exactly one per proposal, reasons in Simplified Chinese, with one repair call. Status `ok`, `unusable`, `failed` (provider error or spent budget; nothing more is sent) or `skipped` (no term proposal, nothing sent). Its own budget is `curator_budget` (default 20,000 tokens). Without decisions every term stays `undecided` and the Run still succeeds; `apply` still applies names, confirmations and conflicts.
  - **Failures.** A failing `apply` fails the Run through `RunCrashed` and writes nothing. A failure after `apply` (in `finish_run`) leaves the KB written under a failed Run (OUTLINE §3.3, still open).
  - **KB reach.** The Run's attempts record `kb_snippets`: the kind, key and status (`approved` or `pending`) of each item the snippets part showed, in prompt order, even when the Orchestrator failed. `KBSnapshot.snippet_items` gives those items and `snippets()` is built on it. `runs._shown_snippets` repeats `kb_snippets_part`'s page-text join, because `agents/` could not change (`IDEAS.md`); tests compare the record with the request.
- The Knowledge Base (`kb/`, OUTLINE §3.3):
  - **Tables.** One `kbs` row per KB; entries, profiles and proposals belong to one KB. The eval harness makes one KB for each `full` eval run (purpose `eval`, labelled with the eval id), and nothing carries over between eval runs.
  - **Readable states.** `kb.loader.load_snapshot` returns an immutable `KBSnapshot` of the `approved` and `pending_human` entries and profiles. It holds no connection, so it is safe in tool handlers. The tools describe the two states as "in the knowledge base" and "proposed on an earlier page, not yet confirmed by a person".
  - **Proposals.** `ProposalCollector` validates proposals and gives each a content-derived ID (KB, page, kind, normalised pair), under a lock. Payload strings refuse control characters and line separators, so every stored entry renders as exactly one snippet line.
  - **Agents** get only a snapshot and a collector, never a connection, and that holds for the whole import graph: `kb/loader.py` and `kb/curator.py` are the only `kb/` modules that import `store`, `fukidashi.kb` exports neither, and a test imports the agents and the Orchestrator in a fresh interpreter and checks that `fukidashi.store` and `sqlite3` stay unloaded.
  - **Writes.** `curator.apply` applies one page's proposals and the Curator's decisions in one `store.transaction`, by the code rules: duplicate, confirmation, conflict, rule 6 (a character whose name or alias matches exactly one readable profile with an agreeing rendering joins it: `store.add_profile_aliases`, a `merged` history line and the result `merged`; a disagreeing rendering or several matching profiles is a `conflict` and writes nothing), a conflict across kinds (a term whose source is a readable profile's name or alias, or a character whose name is a readable entry's source, goes to `pending_human`, writes nothing, and has its own result, `conflict_across_kinds`), name to `pending_human`, accepted / rejected / undecided term. It is the only caller of the functions in `store.KB_WRITES`, which a test enforces with `ast`. It must be called with no transaction open.
  - **The gold glossary never seeds the KB.**
- `backend/tests/test_kb_seams.py` pins the bytes of every agent request over 16 scenarios (`backend/tests/request_scenarios.py`), KB off and on, as digests re-baselined at #53 (the M5 tuning). An unintended change to a prompt, a tool schema or the request layout fails it. An intended one re-baselines the digests in the same PR. The Curator's prompt is not among the scenarios, so nothing pins it (`IDEAS.md`), and after `exp-frozen` no prompt may change.
- Prompts contain only `text_ja` and the boxes. `segments` also stores the reference translations (`text_zh_hant`, `text_en`); they must never reach a prompt of the system's agents. (The one place a reference goes to a model is term consistency's extractor check, which sends the converted reference to the judge on purpose, as evaluation, never to the system.)
- A segment's `idx` (its position in `annotation.json`) is the region id in the prompt, the badge on the image and the row order. Import upserts with `ON CONFLICT DO UPDATE` so row ids stay stable; `INSERT OR REPLACE` would orphan `translations`.
- A Run is inserted as `running`, then finished. A failed Run stores `error` and `attempts_json` but no translations, and the page keeps showing the latest *succeeded* Run, whatever its config. A `baseline` Run's `attempts_json` is a list with one attempt per call, a failed request included (that attempt has `error` and its `record`); a `translator` Run's is a dict (`config`, `agent` with its steps, `repair`, `fallback`); a `full_no_kb` Run's is a dict (`config`, `stages` in order, each with its kind, status, error, the agent's own record and its flags or verdict and issues, then `send_backs` and `final`); a `full` Run's is the same plus `kb_snippets` and `finalize` (null when the Orchestrator failed; otherwise `kb_id`, the Curator's status, decisions and record, and each proposal's result); a `RunCrashed` Run keeps `[]`. Empty or unparseable model output (DeepSeek sometimes returns empty content) is retried once, then the Run fails; output whose region ids are not exactly the page's ids (missing, unknown or duplicate) counts as unparseable. A `ProviderError` fails the Run at once, without a retry: the request may have been billed, and OUTLINE §3.6 leaves resending to the user. Once the Run row exists, an unexpected exception marks the Run failed before it propagates. Only a killed or interrupted process (Ctrl-C), or a database that fails during that recovery write, leaves a Run `running`.
- A human edit (OUTLINE §8, "How a human edit is stored") is a Run of config `human`, written by `runs.edit_translation` and reached through `PUT /api/pages/{book_title}/{page_index}/segments/{idx}/translation`, which answers the page's `PageDetail`. `human` is not in `runs.CONFIGS`, so `translate_page` refuses it. Its base is the page's latest succeeded Run of any config: the new Run holds the base's Translations with one Segment's text replaced, stored exactly as sent, and its `attempts_json` is a dict (`config`, `base_run_id`, `edits`: a list of `idx`, `before`, `after`, so that a rename can edit several Segments in one Run). It makes no call: 0 calls, tokens NULL, cost 0.0, model `human`, `config_json` `{}`. Unlike other Runs it is inserted already finished: `store.insert_human_run` does not commit, and `edit_translation` reads the base and writes the Run and its Translations in one `store.transaction` (`BEGIN IMMEDIATE`), so a failure leaves no Run, no `running` row and no Translations, and two edits at once are both kept. A refusal records no Run: `EmptyTranslation` (empty or only whitespace, 422), `PageNotFound` or `SegmentNotFound` (404), `NothingToEdit` (no succeeded Run, 409); `EmptyTranslation`, `SegmentNotFound` and `NothingToEdit` are `runs.EditError`s. The text is otherwise unchecked (`IDEAS.md`). A text equal to the current Translation records no Run. A later succeeded Run of any config supersedes the edit, which stays stored, and `previous_pages` reads Runs of the agent's own config, so a human edit reaches no agent (`IDEAS.md`).
- `runs.py` raises domain errors (`PageNotFound`, `NothingToTranslate`, `ImageMissing`; the client factory raises `LLMNotConfigured`), never `HTTPException`; the router does the mapping. These `TranslateError`s mean no Run was recorded. `RunCrashed` (carrying `run_id`) means a Run was recorded and marked failed; in the API's background thread it is logged, and the Run's `run_end` reports it. `validate_page` runs the same checks without a Run, and the eval harness calls it for every page before the first model call. `translate_page` takes a client factory so each Run gets its own `Meter` and its usage is its own. It picks the pipeline by `config` (`runs.CONFIGS`: `baseline`, `translator`, `full_no_kb`, `full`; `full` also takes `kb_id`); Translate in the API runs `baseline` or `full` (`background.EDITOR_CONFIGS`), and the eval harness chooses among all four. For `full_no_kb` and `full` the eval harness also reports `send_backs`, `final_stop`, `final_reviewed` and the review statuses per page, and counts pages by `final_stop` in `scores.json`. For `full` it makes the eval run's KB after every page is validated and before the first page (the manifest records it as `kb`), reports `curator_status` and `proposal_outcomes` (a count for each of the 9 results) per page, and in `scores.json` the totals and the KB's size at the end. It also reports `kb_reach`, per page and in `scores.json`, with a `kb reach` summary line:
  - **Per page:** snippets by kind and status; lookups per agent and tool, found and not found, counted from the stored steps (calls that never ran do not count); and the distinct items that reached the page.
  - **Unknown is not 0:** a Run without `kb_snippets`, stored before #40, has `snippets: null`, and the totals count it as `unknown`, not `empty`.
  - **In `scores.json`:** `snippet_pages` (nonempty, empty, unknown), the lookups summed, and `items_reached`.

  The harness builds the first page's client before the KB and the output directory, so an `LLMNotConfigured` stop leaves neither; every page still gets one client of its own. It writes its outputs after every page (`scores.json` and `manifest.json` replaced through a temporary file, the page's lines appended to `segments.jsonl`): `finished_at` stays null until the last page is done and pages not yet reached are `pending`, so an interrupted eval keeps the pages it finished. It is not continued, only run again (`IDEAS.md`). Without `--pages` the CLI evaluates every page of the book in page order (`store.book_page_indexes`). On Ctrl-C `eval/run.py` prints where the finished pages are (any exception that leaves `run_eval` after the output directory exists carries it as `out_dir`) and exits 130; a Ctrl-C inside `translate_page` still leaves that page's Run `running`.
- Tracing (`tracing/`, OUTLINE §3.5, §8): off unless `FUKIDASHI_TRACING` names a backend (`phoenix` is the only one). Entry points (the API's `lifespan`, `eval/run.py`, the smoke script) call `tracing.setup()` once; library code never does. `runs.translate_page` runs inside `tracing.page_span`, so one page is one trace (for `full_no_kb` and `full` its root span also carries `send_backs` and `final_stop`, and for `full` `curator_status` and a `proposals_<result>` count for each result; the stages have no spans of their own); `Outcome.trace_id` carries its ID, and so does `trace_id` on every exception that leaves `translate_page` once the span is open (`RunCrashed`, and whatever stops a page before its Run exists; None when tracing is off), so eval rows and the manifest record it for failed pages too. Every exporter is wrapped in `redact.RedactingExporter`, which replaces data-URL images and the value of `LLM_API_KEY` in span and event attributes: `hide_input_images` alone is not enough, because the LangChain instrumentor writes whole conversations, images included, into `input.value`. The Phoenix endpoint must be on this machine, and whatever is specific to a backend lives in its one function in `tracing/backends.py`, so another backend is another function there. The exporter sends spans straight to that endpoint: its `requests` session ignores proxy variables and netrc, and `OTEL_EXPORTER_OTLP_*ENDPOINT` does not move it. Tracing never fails a Run: spans leave through a batch processor and exporter errors are only logged. Before the first page, `eval/run.py` exits 2, with no Run, when a LangSmith variable is on or tracing refuses to start.
- The live trace (`live_trace.py`; OUTLINE §0, Live trace event; §8, "Where the live trace's events come from") is not tracing: it reads no span, and tracing reads no event. `runs.translate_page(..., on_event=sink)` reports each step of the Run to `sink` as it happens, as a `RunEvent` (`run_id`, `seq` from 1 rising by 1, `kind`, `data`).
  - **The hook.** Inside the Run it is an `emit(kind, data)` (`live_trace.Emit`), passed down to `run_orchestrator`, `run_translator`, `run_reviewer`, `run_curator` and `run_agent`, `None` by default. With `None` every request and every stored Run is what it is without a live trace: tests check it over the four configs and the 16 scenarios (`request_scenarios.collect(page, emit=...)` still gives the pinned digests). The eval harness passes no sink.
  - **The kinds** and their fields are in `live_trace.py`'s docstring: `run_start`; `stage_start` and `stage_end` for the Orchestrator's stages and finalize; `model_call` and `tool_result`, which `run_agent` reads from the agent's stream; `repair`; `fallback`; and `run_end`, the last, emitted after the row is finished and equal to it. `baseline` emits only `run_start` and `run_end`, and a page refused before its Run exists emits nothing.
  - **What an event never carries:** the page image, the user message, the reasoning text (only `reasoning_chars`) or a Reference translation.
  - **The sink** is called only in the thread that called `translate_page`: tool handlers run elsewhere, but the events come from the stream loop, so `seq` needs no lock as long as one thread owns the Run. Each `data` is a JSON copy, so a sink cannot change the stored attempts. A sink that raises never fails the Run: the first exception is logged as a warning naming the Run, and the sink is not called again for that Run.
  - **Storage.** `runs.store_events(conn)` is the sink that stores each event in `run_events` through `store.add_run_event`. That commits at once, so another connection reads the events while the Run is `running`, and raises `RuntimeError` inside an open transaction, so a Run that stores its events needs a connection of its own. `store.run_events(conn, run_id, after_seq)` returns the events after a `seq`, in order. The API's background Runs store their events this way; the eval harness passes no sink.
- Running pages from the editor (`background.py`, `api/runs.py`; OUTLINE §8, "Running pages from the editor"):
  - **Translate.** `POST /api/pages/{book_title}/{page_index}/translate` takes an optional body `{"config": "baseline" | "full"}` (default `baseline`; another config or an extra key is a 422). `BackgroundRuns.start` runs `runs.translate_page` in a thread of its own, and the route answers `202 {"run_id"}` once that Run's `run_start` has arrived: the request waits for the Run to exist, never for the model. A page refused before its Run exists keeps its mapping (404, 422, 503). A Run that fails later is reported by its `run_end` and by the page, never by the POST.
  - **One Run per page.** A page with a Run of this process that has not ended, or with a `running` row in the database, answers 409 and records nothing; the check and the start are one step under a lock. `PageDetail.running_run_id` is the page's `running` Run (the latest), so a reload finds the Run to watch.
  - **The thread** has its own connection (opened from `get_db_path`), its own client from `get_client_factory`, and `runs.store_events` on that connection as its sink. It hands the route the Run's id before that event is stored, and closes the connection whatever happens; a `RunCrashed` there is logged, and the Run's `run_end` reports it. `full` uses the book's Editor KB (`store.editor_kb`: `purpose` and label `editor`, made on first use, one row per book under the `UNIQUE` constraint). A 503 on `full` can leave that KB empty, which is harmless.
  - **The stream.** `GET /api/runs/{run_id}/events` (FastAPI's `EventSourceResponse`) sends the stored events after `Last-Event-ID` (missing → 0; anything but digits → 422) as `id = seq`, `event = kind`, `data = data`, then polls `run_events` every 0.25 s while the Run is `running`. It ends once the Run is over and every event is sent, with one poll more when the last event sent is not `run_end` (`translate_page` stores `run_end` after finishing the row). A Run that is over with nothing after `Last-Event-ID` answers 204, which stops the browser's `EventSource` from reconnecting; an unknown Run is a 404. The 204, 404 and 422 come from a dependency (`requested_events`), because FastAPI treats a generator path operation as a stream.
  - **Stale Runs.** At start the API's `lifespan` marks every `running` Run failed (`store.fail_stale_runs`, error `main.STALE_RUN_ERROR`) and logs how many. It cannot tell a stopped server's Run from one that an `eval/run.py` is running at that moment, so do not start the API while an eval runs.
  - **The timeout.** `LLMClient(timeout=...)` passes the SDK a request timeout only when set. As the API's dependency, `get_client_factory` gets `API_REQUEST_TIMEOUT_S` (180 s); called directly, as `eval/run.py` does, it gets None, so the eval's clients and requests are what they were.
  - **Shutdown.** An open event stream keeps uvicorn's graceful shutdown waiting: with a stream open on a running Run, one Ctrl-C did not stop it in 20 s. Start the backend with `--timeout-graceful-shutdown 5` (the documented command); with it, Ctrl-C stops the server about 5 s later.
  - **The editor** posts the select's config and watches the Run with `EventSource` (`api.watchRun`). On `run_end` it refetches the page, and it shows a failed Run's error. A 409 shows as "already being translated", and a stream that ends without `run_end` says so. On load, a `running_run_id` makes it watch that Run. It does not show the events yet.
- Tests replace the FastAPI dependencies `get_db`, `get_db_path`, `get_dataset_root`, `get_client_factory` and `get_background_runs` (a fresh registry per test) and use `FakeClient` and its variants (`UsageClient`, `CrashAfterCallClient`) from `backend/tests/conftest.py`. To test `LLMClient` itself, `mock_llm_client()` runs the real client and SDK on an `httpx.MockTransport` (responses built with `completion()`), so nothing leaves the process; the agent loop's tests (`test_agent_loop.py`) script the provider the same way. `FakeClient.chat` takes no `tools`. An autouse fixture in `conftest.py` clears the LangSmith tracing variables, `LLM_JSON_MODE`, `FUKIDASHI_TRACING` and `PHOENIX_*`, and calls `tracing.shutdown()` after each test, so a shell's variables cannot change the suite. Tracing tests plug an in-memory backend into `tracing.BACKENDS`, the same seam Phoenix uses.
- Eval references are `text_zh_hant` converted with OpenCC `t2s` (OUTLINE §8); hypotheses are the Run's stored Translations. Eval outputs live in `runs/eval/` (gitignored).
- The gold glossary (`eval/gold_glossary/<book>.json`, OUTLINE §4.7) is evaluation data only: it never seeds the KB or reaches a prompt, and nothing outside `evaluation/` and `eval/` refers to it. `evaluation/glossary.py` checks it against `annotation.json`, never the database; `evaluation/splits.py` is the one place that names the dev and test books. Files in git hold terms only (at most 20 characters each); candidate lists and review sheets quote the dataset and stay in `runs/glossary/`. Every entry has a required boolean `borderline` (15 of the 37 dev entries). The three test books have their glossaries too (27, 21 and 28 entries), built before any of those books was translated; the author approved the drafts and does not read Japanese. `check` looks for every target and variant in the converted references, except a variant that is the target in mainland forms (OpenCC `tw2s`), which `t2s` never produces.
- The scorers read a finished eval run (`finished_at` set) and write their own file next to its outputs, through a temporary file; they refuse an unfinished one with exit 2 and write nothing. The judge-based scorers (GEMBA-MQM, term consistency) do the same through the judge's own client and ledger.
  - **GEMBA-MQM** (`evaluation/mqm.py`, `mqm_scorer.py`, `eval/mqm.py`) sends the judge only the Japanese source and the Translation, one call per segment with a non-empty Japanese text (an empty one is `skipped`), and writes `mqm-<model>.json` (the model in the name, so one run can hold several judges' files). The prompt template, three examples, parser and weights are GEMBA's, at a pinned commit and under **CC BY-SA 4.0**: `evaluation/mqm.py`, `backend/tests/test_mqm.py` and `docs/mqm-annotation.md` carry a notice at their top and are listed in `LICENSE`; keep it when editing them. A segment's `span` is unreliable (`IDEAS.md`); `text` keeps the judge's whole line. `--reparse` reads stored answers again with the current parser, with no call; an answer made only of "No-error" lines counts as no error.
  - **The labels come before the judge.** The agreement sample's labels are Claude's, not a person's, and their sha256 is recorded in OUTLINE §4.5 before any judge output on the sample; `eval/mqm_agreement.py` refuses a sheet whose hash differs, and records who annotated (`--annotator`, default `llm`). Neither judge passed, so the report's MQM block says "for reference only".
  - **Term consistency** (`evaluation/consistency.py`, `eval/consistency.py`, OUTLINE §4.7) asks the judge, once per occurrence and per text (the Translation and the converted reference), to extract the rendering of a gold glossary term, and writes `consistency-<model>.json`. It is strict: renderings that contain one another count as different.
  - **Term accuracy** (`evaluation/terms.py`, OUTLINE §4.7) reads only `page_index`, `idx`, `ja`, `hyp` and `ref_zh_hans` of `segments.jsonl`, never the database or `ref_zh_hant`, and writes `terms.json`.
  - **COMET** (`eval/comet.py`) imports only the standard library at the top and `comet` and `torch` inside `load_scorer`. `pyproject.toml` and `uv.lock` never gain COMET or torch. It writes `comet-<model>.json`, and its tests (`test_comet_script.py`) use a fake scorer, so the suite needs no torch. It records the checkpoint's Hugging Face revision (`model_revision`, from the snapshot path, or null).
  - Both read `segments.jsonl` split on `"\n"` only, never `splitlines()` (the harness writes U+2028 and U+0085 unescaped), and term accuracy refuses a repeated `(page_index, idx)`.
- The pooled report (`evaluation/report.py`, CLI `eval/report.py`) reads only files: each eval run's `manifest.json`, `scores.json`, `segments.jsonl`, `terms.json`, COMET file, consistency file and MQM file, and the glossary (for its hash); no database, model or network. A run holding more than one judge's MQM file needs `--mqm-judge`, and `--mqm-agreement` adds the agreement outcome. It takes one finished eval run per config and book, over the same books for every config. Quality numbers cover only the common pages (scored by every config, per book), and the pages left out are listed; spend covers all Runs. chrF / BLEU are recomputed over the pooled segments, COMET is joined by `(book, page_index, idx)`, term accuracy pools hits and occurrences, and unknown stays `None`. Inputs that do not belong together (another eval id, a COMET file over another `segments.jsonl` or another model, another glossary, two runs of one config and book) are refused with exit 2 and nothing written; provenance (a dirty tree, different commits or models) is a warning. It writes `runs/report/<UTC time>-report/report.json` through a temporary file and prints a summary. It gives no confidence intervals; the paired bootstrap does.
- The paired bootstrap (`evaluation/bootstrap.py`, CLI `eval/bootstrap.py`; `eval/PROTOCOL.md` "Statistics", OUTLINE §8) reads only files, through the report's own code: it runs `report.build_report` first, so it refuses what the report refuses, and it also needs exactly `baseline`, `full_no_kb` and `full`, every run with its consistency and MQM files. For `full` vs `baseline` it gives COMET (primary), chrF, BLEU, term accuracy, term consistency and MQM; for `full` vs `full_no_kb`, term accuracy (primary) and term consistency. Each comparison uses its own pages: those both of its configs scored, which can be more than the report's common pages. 10,000 resamples, a `random.Random(2027)` per comparison; a page drawn twice counts twice in every metric; the interval is the 2.5th to 97.5th percentile of `full` minus the other config. MQM's interval is for reference only, and a comparison's consistency interval is too when any of its runs (one config on one book) has an extractor accuracy under 90% on the comparison's pages. Its details were fixed before the first test page, so do not change them now; its tests check that the full-sample values equal the report's pooled ones. The official output on the test runs is `runs/bootstrap/20261101T023151Z-bootstrap/bootstrap.json` (#61): it was computed once, and a check of it goes to a scratch `--out-root`, never to `runs/bootstrap/`.
- The cost / latency summary (`evaluation/costs.py`, CLI `eval/costs.py`; `eval/PROTOCOL.md` "Statistics", OUTLINE §8) reads only files and never writes to the ledger. It runs the report's own checks first, so it refuses what the report refuses.
  - **Ledger ranges.** The ledger has one line per call and no run id, so each eval run's lines are given (`--ledger-range <eval id>=<first>-<last>`, counted from 1, both included). A range that is not the run's calls is refused: it must split into one run of one `page_id` per attempted page, in the manifest's order, as long as `calls` for a scored page, made with the model the run asked for, and no two ranges may overlap.
  - **Prices** are recovered from those lines, not read from `.env`, and must fit exactly.
  - **Figures.** For each config, pooled and per book, on the common pages and on the attempted pages: calls per page; tokens per page (uncached input, cached input, output); the cached share of input; cost per page as a range (lower: cached input at $0; upper: the ledger's cost; `--cached-input-price-per-m` adds a value at that price); latency p50, p95 and mean.
  - **Unknown is not 0.** A failed page's calls count in the attempted pages. A figure with a line without usage or cost in its scope is null, never a partial sum, so `n/a` is what the attempted view shows for the cells with failures; `runs[]` keeps the sums over the lines that have them. These figures are not billed amounts.
  - **Output.** `runs/analysis/<UTC time>-costs/costs.json`, through a temporary file, and a printed table. The official output on the test runs is `runs/analysis/20261101T035019Z-costs/costs.json` (#63): a check of it goes to a scratch `--out-root`, never to `runs/analysis/`.

|---|---|---|---|
| Architect | `/architect` | Explains and steers the project with the user, edits plan docs (`OUTLINE.md`, `IDEAS.md`, `docs/`; `SCOPE.md` only at a checkpoint), writes tasks | Edits code, runs real LLM calls |
| Executor | `/execute-task NNN` | Implements one task on branch `task/NNN-slug`, verifies, commits, writes the Execution report | Edits the task's goal or criteria, widens scope, pushes, opens a PR, merges |
| Reviewer | `/review-task NNN` | Fresh context: checks the branch against the task, writes the Review and a verdict | Edits or commits repo files; trusts the Execution report without reproducing it |

Task files live in the main checkout's `tasks/` directory (gitignored), so every session sees them whether it runs in the main checkout or in a worktree. Resolve the directory with:

```bash
TASKS_DIR="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")/tasks"
```

The format is `docs/task-template.md`; the file is `$TASKS_DIR/NNN-slug.md`. The architect owns everything above `## Execution report`, the executor owns `## Execution report` and the `branch:` field, the reviewer owns `## Review`. Each role changes `status:` only for its own transitions:

```
proposed → in_progress → in_review → approved → done
```

- Executor: `proposed` or `changes_requested` → `in_progress` → `in_review`, or back to `proposed` when blocked (with a note).
- Reviewer: `in_review` → `approved` or `changes_requested`.
- Architect: `proposed`, `cancelled`, and `done` once the user has merged (record the PR number).

One task is one PR. The executor works in a git worktree of its own next to the main checkout (`<main checkout>-task-NNN`), on branch `task/NNN-slug` from a fresh `origin/main`, never in the main checkout: sessions in one checkout share one `HEAD`, so one session's `git switch` moves another's branch. The main checkout belongs to the user and the architect; after the merge the worktree is removed with `git worktree remove`. The executor refuses to start in a working tree that has changes it did not make, stages explicit paths (never `git add -A`: another session may have left files), and may commit on its task branch, because being assigned the task is the authorization. Pushing, opening the PR and merging happen only when the user says so. Real LLM calls happen only if the task's Constraints allow them; the reviewer makes none unless they do too.
